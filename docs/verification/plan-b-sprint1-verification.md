## Implementation and trust boundary

One supported fixture, `synthetic-oracle-ratio-v1:wrongful-liquidation:v1`, lives in a server-owned
versioned catalog. Its exact serialized bytes have digest
`sha256:69923abc94cd83722f8785400ba227849104f71e5697786649f0564626923153`.
Callers select this reference/digest and supply the linked policyId, incidentId and exact observedAt;
they cannot supply facts, a verdict, an executable verifier, a file path or an external URL.

`verifyClaimFixture` resolves the actual ClaimsCase, enforces role/ownership and an open evidence
investigation, and checks the confirmed synthetic policy/incident/exposure association and incident
window. Procurement policies require the existing healthy, fresh canonical bind checkpoint through
`claimsPolicyContext`. It executes the existing `createSyntheticOracleEvidenceProvider` and
`createSyntheticOracleVerifier` server-side. It does not execute a coverage or settlement rule.

Migration 011 adds an append-only `claim_verifications` table with case FK and unique case/request
digest; SQL triggers reject update/delete. Each execution records submitted inputs, fixture reference
and digest, exact catalog fixture inputs, version, generated facts, findings, status, actor/time,
request digest and policy/incident context digest. Record and audit append share a transaction.
Concurrent case or provenance changes reject persistence; exact duplicate requests reuse the original
record. Replay rechecks access and refuses a changed policy/incident context. A failed execution
is durably recorded as failed/invalid; an exact retry returns that failure rather than hiding it.

Outcomes distinguish execution (`completed`, `rejected`, `failed`) from required fixture evidence
(`sufficient`, `missing`, `contradictory`, `invalid`). **Sufficiency applies only to this fixture
consistency check**, not to all claim evidence or adjudication prerequisites. Unknown/missing fields,
wrong digests, mismatched links/times and unsupported provenance fail closed. All external attestations
are currently unsupported and rejected, including stale ones; this integration does not implement
external signature verification or freshness validation for accepted attestations. The separate bank
examiner and research causal verifier remain separate and are not exposed by this endpoint.

Every result says `authenticity: synthetic_fixture`, `independentlyAuthenticated: false` and includes
an explicit limitation finding. Consistent ratios show only what the deterministic synthetic fixture
asserts: understated adapter ratio and a supplied healthy replay flag. They do not prove that an
external liquidation happened, authenticate external sources, establish real causal truth, establish
policy event applicability, or substantiate actual economic loss. Merely linking a fixture to an
incident is not independent event evidence. The fixture's illustrative deductible is not the policy
settlement deductible and no payable is inferred here.

## API

- `POST /api/claims/cases/:id/verification` executes the supported fixture. Authenticated claimant,
  reviewer, authority or system principal required; existing policy access checks, API security,
  origin and request limits apply. Max envelope size 16,000 characters. Malformed JSON returns 400;
  a well-formed but invalid evidence envelope produces a persisted rejected record. Unauthorized
  requests do not write records. Case and policy identity are checked again inside the service.
- `GET /api/claims/cases/:id/verification` is read-only and returns `verifications` for accessible
  cases. Existing `GET /api/claims/cases/:id` also includes this additive field.
- Read data class: `synthetic_fixture_verification`. Historical results are execution records,
  not a guarantee of current policy eligibility; changed provenance cannot safely replay success.

Example body (use actual accessible IDs and the incident's exact timestamp):

```json
{
  "fixtureRef": "synthetic-oracle-ratio-v1:wrongful-liquidation:v1",
  "fixtureDigest": "sha256:69923abc94cd83722f8785400ba227849104f71e5697786649f0564626923153",
  "policyId": "<actual-policy-id>",
  "incidentId": "<actual-incident-id>",
  "observedAt": "<exact-incident-observedAt>"
}
```

A real in-memory execution record is preserved in
[example-verification.json](plan-b-sprint1/example-verification.json). It was generated by:

```sh
pnpm --filter @arcuex/insurance exec node --import tsx examples/claim-verification.ts
```

The example creates a legacy synthetic policy and linked incident in memory; fundingVerified is an
explicit demo input, not live financial proof. The authenticated API test separately exercises a
canonical procurement policy with mocked reconciliation evidence. Neither is a live bind.

## Compatibility and review

Existing ClaimsCase states, row versions, authenticity, manifests, evidenceRoot, adjudication,
settlement authority, history and money/accounting paths are unchanged. The new service does not
append an evidence manifest or change case authenticity automatically: a fixture result cannot
silently satisfy the existing approval gate. The existing reviewer flow remains responsible for
appropriate evidence, coverage and loss amounts. Automatic consumption by a future guided UI and
adjudication integration require separate review. No automatic approval or payment is added.

Migration 011 is additive; migrations through 010 remain byte-for-byte unchanged. Fresh/upgrade
migration regression tests continue to preserve existing case bindings, policies and history.
The table has no FK directly to policies because the case already supports legacy/procurement
policy identities. Two migration-count assertions move from 12 to 13. Rollback must preserve new
verification records; do not delete audit history or run production migrations during review.

Changed files: insurance `claim-verification.ts`, its tests and example, and barrel export;
persistence migration 011, migration list, repository append/read methods and two count assertions;
web verification route, additive case GET and authenticated integration test; README and this report,
example and validation artifacts. No contracts, onchain pipeline, authority configuration or UI changed.

Validation: 273 application tests pass (including 18 new verifier cases and one new authenticated API
case); typecheck/lint/build and exact logs are recorded in [the validation file](plan-b-sprint1/verification-validation.md). Negative coverage
includes missing/manipulated evidence, wrong policy/incident, invalid/future/out-of-window timestamps,
unsupported stale attestations, foreign reads/writes/replays, failed and negative verifier execution,
concurrent provenance changes and immutable SQL records. All tests use in-memory DBs/mocked chain.

Before merge: review the fixture-only sufficiency semantics and additive API, audit auth/provenance
checks and migration preservation, require green CI on the exact commit, and agree how the future UI
will present historical results without implying an independent loss oracle. A merge does not approve
a deployment, production migration, capital action or broadcast. The settlement analysis is on the
separate `analysis/plan-b-sprint1-settlement` branch at the same baseline.
