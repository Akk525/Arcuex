# Arcuex backend integration v1

The [machine-readable contract and response examples](backend-integration-v1.json) use synthetic data throughout. The examples marked partial omit fields unrelated to the transition. The signing example deliberately omits executable calldata.

Use same-origin requests and the existing HttpOnly wallet session for procurement and claimant actions. Reviewer and authority credentials belong to authorized operator sessions. All token amounts use decimal strings. A field ending in `Micros` uses six decimals. Quote, policy and delegation times are epoch seconds. Evidence `validUntilMs` is epoch milliseconds. `signBefore` is an exclusive UTC ISO timestamp.

| Stage | API | Integration behavior |
| --- | --- | --- |
| Discover and quote | `GET /api/procurement/products`, `GET /api/procurement/capacity`, `POST /api/procurement/quotes` | Use the product code and version returned by the catalog. Fixture mode exposes synthetic terms and disables financial actions. `capacityStatus` is an advisory observation outside the digest. `verified` means capacity covered that quote at the check. It does not reserve capital. |
| Delegated authority | `GET /api/procurement/delegations`, `POST /api/procurement/authority` | Display validity, limitation and remaining premium. Bind permissions to the authenticated wallet and the original grant. Grant scope covers agent, position, product, beneficiary, expiry and premium/limit caps. The independent pilot is owner-purchased. |
| Accept and pay | `POST /api/procurement/accept`, then `POST /api/procurement/payment` with `stage: approve` or `bind` | Accept the exact digest and keep the returned policy ID. The accepted payer approves USDC and binds in separate wallet actions. The staged bind checks capacity, balance, allowance, expiry and exact calldata simulation. Register the approval hash at `/api/procurement/approvals` and the bind hash at `/api/procurement/confirm`. Retry the same hash during receipt delay. Refresh the quote after expiry. |
| Activate policy | `GET /api/policies/{policyId}/lifecycle` | `confirmed` is a canonical indexed link. Coverage starts at the policy's effective time. Check `claimsEligible` for the current principal. An orphaned or incomplete link cannot activate claims. `fixture_ready` represents a rehearsal snapshot. |
| Verify and adjudicate | `POST /api/claims/cases`, `POST /api/claims/cases/{id}/verification`, then `POST /api/claims/cases/{id}` with `action: adjudicate` | Independent verification takes the replay/recovery envelope. Use only the current verification ID, canonical context and freshness cutoff. A reviewer or authority records coverage and contractual review. Model output is advisory. |
| Prepare and authorize signing | `POST /api/claims/cases/{id}` with `prepare_settlement`, then `authorize_settlement_signing` | Preparation records the frozen intent and returns the prep ID and deadline. It omits transaction calldata. Signing authorization requires a fresh authority session, the prep ID, the current external signer address, and the exact recipient, amount, loss key and evidence root from the decision. |
| Reconcile a payment | `mark_paid` or `mark_failed` on the same claim endpoint | Submit the observed hash. Two descendant blocks and the original canonical receipt are required. `mark_failed` requires a matching confirmed revert. A successful callback must match the authorized account and nonce, calldata, policy, claim, transfer and inclusion interval. Use `paymentFinality` and `confirmedSettlementReceipt` from reads for display. |

## Controlled authority

The backend holds no settlement signer credentials. The existing claim endpoint can authorize one exact unsigned transaction for an authority address and nonce. Immediately before an approved signing operation, the external operator must request authorization, use the returned account, nonce, target and calldata with zero native value on chain `5042002`, and enforce `signBefore` locally before both signing and submission. The request revalidates the human decision, current evidence root and canonical verification, onchain policy, current and confirmed authority, wall and chain deadlines, settled flags, pending and canonical nonces, and exact-call simulation. The application journals the authorization against the existing preparation. Generic transaction helpers and the legacy lifecycle runner reject live settlement.

The settlement paths are the secured claim mutations, the pure ABI builder, the lifecycle CLI and the external wallet. The old claims pipeline updates the synthetic SQLite ledger. The historic receipt endpoint and indexer are read and reconciliation paths. They confer no signing authority.

An issued account/nonce remains held across restart, including after expiry, a timed-out API response, or a wallet rejection without a receipt. Investigate the account/nonce and existing hash. The API does not reissue the same authorization. A canonical confirmed revert permits a fresh preparation and nonce while the approval is still current. A reverted receipt that loses canonicality blocks a new authorization. Earlier preparations without this protocol marker require manual receipt audit. An orphaned successful payment returns to pending with its original commitment and audit events. An existing transaction that reappears canonically can be reconciled with its original authorization and inclusion deadline.

The contract enforces the onchain authority, coverage window, beneficiary and reserve/loss accounting. The contract does not consume backend evidence or enforce `signBefore`. A direct external wallet call can bypass the application. Provider pending state also cannot prove that privately held signed transactions are absent. Live settlement requires a dedicated external signer workflow that uses this gate and excludes alternate submissions. An expired transaction that is nevertheless included onchain requires manual incident reconciliation.

## Displaying payment finality

`confirmed` means a recorded verified receipt still matches a canonical block at the required depth. `unverified` covers shallow confirmation, missing proof, RPC outage or inconsistent replies. `reorged` means the receipt is off the canonical chain, or the worker has already reopened the case. `not_paid` covers unpaid cases and fixtures. Claim reads suppress the receipt and present an unconfirmed stored payment as pending while the worker reconciles it. Policy settlement history shows `Payment unconfirmed` in that interval. The historical demo receipt is archival.
